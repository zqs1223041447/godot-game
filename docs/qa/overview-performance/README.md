# 探索总览有限性能定位

基线 `160e05992d69a7d407cbff54947e116bea21031d`。结论：确认并减少了一处重复扫描的CPU开销；**总览整体性能仍未闭环，不宣称性能通过或帧率改善**。

## 方法和原始记录

复用 `overview_live_short_test.gd` 的原37怪密集运行夹具：正式银杏I入场后，将原实体放到玩家附近，仅提高运行时双方耐久；自动攻击、敌人攻击和Main/HUD正常 `_process` 均持续运行。没有新增怪物或修改规范角色。Godot4.6.3，X11 dummy，1280×720，Mesa llvmpipe，独立 `/tmp` 用户目录，每次进程45秒上限。

`instrument.py` 在 `/tmp/godot-overview-profile-src` 生成诊断副本：保留原函数体，将调用包在统一的两次单调时钟与内存记录中。Main、HUD和总览的所有指定函数在开/关两侧使用完全相同的钩子。`profile.gd` 在采样窗内只追加原始 `[标签,开始µs,结束µs,进程帧号]`，不写盘、不额外查询世界状态；采样结束后统一保存。每帧均用同一观察器等待 `frame_post_draw` 并记录墙钟间隔；这不是GPU专用计时。父函数包含子函数时间，不能把各行直接相加。

分开记录 `world_context`、来源组/驻点扫描、最近目标查询、HUD状态刷新、总览状态复制、玩家标记更新、总览 `_draw` 的CPU命令准备、Main固定步长 `tick` 与整个Main `_process`。GPU执行、其他世界绘制、显示同步和OS调度未被单独归因。128次空记录校准p95均约1µs；少量校准离群值保留，不从结果中任意扣除。

- `exploratory-baseline-a/b`、`exploratory-optimized-a/b`：每轮6个交替8帧窗口，a/b使用相反起始开关。沿用了旧夹具“入图后才固定seed”的问题，进程间怪物编排可能不同；**不用于严格的改动前后结论**。原始记录全部保留，旧探针在 `exploratory-probe.gd.txt`。
- `matched-baseline`、`matched-optimized`：修正为入图前固定seed526917，另补一对各4个交替8帧窗口（关/开/关/开）。每次切换后2帧不采样，启动8帧暖机；所有32个采样帧均保留，未删峰值。初始敌人、玩家位置和RNG字节指纹完全相同：`281696ff4a3170f536d3cfcae30e86718a50a5bfe3611ca79e7c8948b1998404`。两轮均15项夹具/只读检查、0失败。
- 每轮动态短测后暂停于该轮密集状态，分别连续采24次相同的查询、状态复制和最近目标刷新；前后完整观察确认战斗状态、RNG和保存字节不变。此部分是固定状态CPU测量，不是持续游玩帧时。
- `summary.json` 保存全部函数/窗口统计；`comparison.json` 仅汇总有效配对。`instrumentation.json` 及各匹配运行目录内的副本记录源文件与诊断副本SHA。基线诊断源由 `git show 160e059:...` 读取，未回滚工作区。

## 测得热点和最小改动

`Main._camp_states()` 原来为3个来源组各扫描一次完整敌人列表，并重复按根ID读取出生记录。现只在**本次查询内**扫描一次、按来源组累加觉醒根怪数量，随后填回原字段；无持久缓存、无跨帧复用，也没有失效策略或延迟刷新。HUD轮询、玩家标记、最近目标查询、地图绘制与清图算法未改。

同编排匹配短测末尾的24次固定状态CPU计时：

| 方法 | 原版中位µs | 改后中位µs | 原版/改后p95µs |
|---|---:|---:|---:|
| `world_context()` | 236 | 171 | 265 / 274 |
| `_camp_states()` | 111 | 51 | 115 / 81 |
| `_outpost_states()`（未改） | 55 | 53 | 77 / 84 |
| 总览 `update_live()`（未改） | 22 | 22 | 41 / 24 |
| 最近目标HUD刷新（未改） | 126.5 | 123.5 | 168 / 215 |

仅可说此夹具中查询中位时间下降65µs、约28%，来源组扫描下降60µs、约54%；查询尾部并未一致改善。实际运行的开启窗口中，单次 `world_context` 中位数原约432–454µs，改后370–378µs，也显示局部收益。

| 版本/窗口 | 开关 | 帧间隔ms | Main每渲染帧ms | 总览绘制准备ms |
|---|---|---:|---:|---:|
| 原版0 | 关 | 91.79 | 17.96 | 0 |
| 原版1 | 开 | 97.91 | 21.06 | 0.241 |
| 原版2 | 关 | 93.06 | 20.36 | 0 |
| 原版3 | 开 | 94.86 | 19.67 | 0.230 |
| 改后0 | 关 | 93.09 | 18.87 | 0 |
| 改后1 | 开 | 97.74 | 20.83 | 0.232 |
| 改后2 | 关 | 98.19 | 21.77 | 0 |
| 改后3 | 开 | 100.97 | 20.61 | 0.233 |

开启的额外帧间隔在两个起始顺序的探索记录中可重复观察，但不等于已确定CPU瓶颈。已计时总览绘制准备约0.23–0.25ms，状态复制约0.02ms（实时受CPU竞争时约0.04ms），额外世界查询每0.2秒一次，均不足以解释全部差异。游戏固定步长每步约3.2–3.5ms，一渲染帧常执行5–6步，构成约18–22ms的可测主步成本；它也会随帧间隔发生追赶变化。剩余较大墙钟间隔尚未归因，不能凭llvmpipe、短样本或跨进程趋势排除回退，也不能宣称本改动解决了总览卡顿。后续若继续定位，应单独测渲染提交/执行和同步等待，本批不扩展。

## 正确性与实际流程

`overview_camp_scan_differential_test.gd` 复用原有限query/lineage/settlement流程，在每个检查点读取冻结的160e059三遍扫描实现，直接比较当前 `world_context().camp_states` 的类型保真字节。**604项检查、0失败，302次旧/新对照，其中158次含实际觉醒根怪**。覆盖混合驻点觉醒、根/后代死亡、最近目标移动/切换、排队后代、重试、返城、清图结算写失败与重试；沿用完整模拟/RNG/保存字节只读检查。冻结方法和SHA见 `camp_states_160e059.gd.txt`。

`overview_query_live_test.gd` 复用原短正常处理流程，并增加打开总览时玩家位置/朝向与真实按住移动后的标记新鲜度检查。**32项检查、0失败**；`live/` 保存实际鼠标瞄准发射、敌人真实致死关闭总览、原生地图准备取消/成功重试及重新打开的结果；该流程的帧数记录只用于功能取证，不并入性能比较。

未改战斗、随机调用、存档schema、模型、内容卡或地图规则；不封包、不跑600秒测试或全套矩阵。
