# v100 cleanup guidance: bounded Main integration

The focused Main regression passed **294 checks, zero failures** across two fresh isolated Godot runs. The three scenario groups contributed 286 checks; the remaining eight are the two runs' fresh-profile setup and inactive-query checks. Godot 4.6.3 exited 0 in both runs, and neither accepted log contains `SCRIPT ERROR:` or `ERROR:`.

- `main-query-result.json` / `main-query.log.txt`: 111 checks, including 107 query-group checks
- `main-lineage-settlement-result.json` / `main-lineage-settlement.log.txt`: 183 checks, including 106 lineage and 73 settlement checks
- `main-result.json`: combined acceptance summary, exact source/log/report SHA-256 hashes and first-failure disposition
- `tests/exploration_cleanup_hint_test.gd`: independently selectable `query`, `lineage`, and `settlement` groups via `CLEANUP_GUIDANCE_GROUPS`

## Scope and fixture

The regression extends the accepted `exploration_main_flow_test.gd` fixture only for its real Main setup, formal-town return, defense settlement, actor lookup and observations. It overrides the runner; it does not execute the previous full suite. All roots enter through current `craft_normal_map` and `start_map` transactions. Descendants come from the original monster runtime and actual root deaths. Completion rewards and unlocks are generated by the existing formal transaction. No equipment, currency, pending reward, spawn record, boss template or lineage is fabricated.

Controlled lethal settlements and runtime positions make the cases bounded and reproducible. They are not natural combat footage, movement acceptance, a performance test or UI timer evidence. The parent task owns HUD scheduling validation. Existing schema is checked for preservation, without pinning an obsolete schema number. Each run starts under a newly created `/tmp/godot-m1-v100-cleanup.*` XDG profile and refuses an existing `user://build_save.json`. The shared import is reused; these runs do not import again.

## Verified behavior

- Real broken-ruins admission starts with 37 actors and six uncleared outposts. Six living roots produce overview; five produce a target. Negative and exactly zero health actors are excluded even when nearer than every living actor
- The query uses current world coordinates for east, southeast, south, southwest, west, northwest, north, northeast and zero-offset `here`. Exact squared-distance ties choose the lower actor ID after reversing the runtime actor array
- A real wall separates the nearest target and player. The getter still returns only a bearing and contains no visibility/path claim
- A naturally generated ginkgo splitter supplies the last outpost root and its real queued descendants. With zero live actors the query reports waiting and no target. Cleared outposts disappear; pending lineage keeps its original outpost present
- A living descendant moved from its initial position uses its current actor position and original root/outpost identity. Authoritative historical spawn position stays unchanged
- The original boss alone has explicit boss identity. Its actual death queues four original children. On admission, all four count as living offspring and the selected child is named `首领后代`, with `is_boss == false`
- All calls compare Main/model/geometry/runtime snapshots, full enemy/queue data, clocks, progress counters, RNG state and exact saved bytes before and after. Mutating returned nested outpost and target dictionaries cannot poison later queries or simulation
- Real formal restart replaces a descendant target with a fresh 37-actor roster and clears its deferred queue. Town return and town restart clear guidance
- After a real 25-root old-garden clear, an injected `_write_bytes` failure produces `settlement`; bytes and completion reward remain unchanged, and return remains blocked by the write failure. Removing the fault and using the original completion retry produces `complete`, the original four-shard pending reward and tier-I unlock. Rechecking completion cannot duplicate progress or mutate saved bytes

## First failure and bounded correction

`main-attempt1.log.txt` and `main-attempt1-result.json` are preserved unchanged. The first attempt had 83 checks with one assertion failure, then a script error: the new fixture incorrectly pinned schema 50 and indexed a wall on the wall-free old garden. These were fixture errors, not production changes. A script error is failure regardless of process exit code.

The fixture was corrected to compare the current incoming schema version and to use the actual walled broken-ruins map with its 37-actor count. Only the affected query group was rerun. The lineage and settlement groups, which had not executed before the first attempt stopped, then ran for the first time. No successful group, old suite, combat soak or performance test was rerun.

## Reproduction

Use the already imported project and a new empty `/tmp/godot-m1-v100-*` directory for each independent invocation. Set `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, and `XDG_CACHE_HOME` below that directory. Run:

```sh
CLEANUP_GUIDANCE_GROUPS=query CLEANUP_GUIDANCE_REPORT=res://docs/qa/v100-guidance/main-query-result.json /usr/local/bin/godot --headless --path . --script res://tests/exploration_cleanup_hint_test.gd
CLEANUP_GUIDANCE_GROUPS=lineage,settlement CLEANUP_GUIDANCE_REPORT=res://docs/qa/v100-guidance/main-lineage-settlement-result.json /usr/local/bin/godot --headless --path . --script res://tests/exploration_cleanup_hint_test.gd
```

Each command needs its own fresh XDG data directory; the guard intentionally rejects a reused profile. Omitting the group selector executes all three groups in order once.
